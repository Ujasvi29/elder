## 1. Design decisions that apply to every table

These are conventions used throughout. Each one is a choice, and each choice has a reason.

### 1.1 Primary keys are UUIDs, not auto-incrementing integers

Every table's `id` column is a `UUID` generated by `gen_random_uuid()`.

*Why:* The mobile app needs to create records while offline or during a bad network moment — an SOS press cannot wait for the server to hand back an ID. With UUIDs the phone can generate the ID itself and sync later without collisions. Sequential integers also leak information (`/users/4` tells an attacker there are few users, and lets them walk the list). The cost is 16 bytes per key instead of 4, which is irrelevant at our scale.

`gen_random_uuid()` is built into PostgreSQL 13+. On older versions you need `CREATE EXTENSION pgcrypto;` — the SQL includes that line and it is harmless if already present.

### 1.2 Timestamps are `TIMESTAMPTZ`, never `TIMESTAMP`

*Why:* `TIMESTAMPTZ` stores an absolute moment in time and converts to the viewer's timezone on read. Plain `TIMESTAMP` stores a wall-clock reading with no timezone, so "the alert fired at 14:32" becomes ambiguous the moment a family member travels or the server moves region. For an emergency product, "when exactly did this happen" must never be ambiguous.

Every table has `created_at` and (where records change) `updated_at`, both defaulting to `now()`. A trigger keeps `updated_at` accurate automatically — see section 6.

### 1.3 Fixed sets of values are PostgreSQL `ENUM` types

Things like alert status (`active`, `acknowledged`, `resolved`, …) are declared as enum types rather than free-text `VARCHAR`.

*Why:* The database itself rejects a typo like `'acknowleged'`. With a plain text column that typo silently becomes a row that no query ever matches — and in this product that means an alert nobody sees. The trade-off: adding a new value later needs `ALTER TYPE ... ADD VALUE`, which is a one-line migration.

### 1.4 Coordinates are `NUMERIC(9,6)`, not `FLOAT`

Latitude and longitude are stored as `NUMERIC(9,6)` — up to 3 digits before the decimal point and exactly 6 after.

*Why:* Six decimal places is roughly 11 cm of precision, far more than consumer GPS delivers, so nothing is lost. `NUMERIC` is exact, whereas `FLOAT` is binary floating point and produces values like `12.971598999999999` that break equality comparisons and look wrong in reports.

**PostGIS is deliberately not used**, per your decision. Geofences and disaster areas are circles — a centre point and a radius. Checking "is this position inside" is straightforward distance arithmetic that works on the phone as well as the server, with no extension to install on every developer machine and on the host. The limitation this accepts: no polygon zones, and no efficient "find every user within 5 km" query. Neither is required by any phase in the report.

### 1.5 Delete behaviour is chosen per relationship, never left to default

Each foreign key declares what happens when the parent row is deleted:

- `ON DELETE CASCADE` — the child is meaningless without the parent, so delete it too. Example: a user's GPS history when the user is deleted.
- `ON DELETE SET NULL` — the child still means something, we just lose the link. Example: an alert acknowledged by a family member who later left the platform. The alert record must survive; we just no longer know who acknowledged it.
- `ON DELETE RESTRICT` — refuse the delete. Example: you cannot delete a caregiver who has bookings; those are financial and legal records.

*Why this matters:* If you leave it unspecified, PostgreSQL blocks the delete with a constraint error, which surfaces as a confusing 500 error in the API months later. Deciding now is cheaper than debugging then.

### 1.6 Money columns are `NUMERIC(10,2)` with an explicit currency

Never `FLOAT`. `0.1 + 0.2` in floating point is not `0.3`, and rounding errors in billing are unacceptable. `NUMERIC(10,2)` handles up to 99,999,999.99. A separate `currency` column (`CHAR(3)`, ISO 4217, default `'INR'`) means the amount is never ambiguous.

### 1.7 Soft delete via `is_active`, not row deletion

Users, contacts and geofences carry an `is_active` boolean rather than being physically deleted.

*Why:* If an elderly user is removed, their alert history must survive for the family's records and for any dispute. Deactivating hides them from the app while preserving history.

### 1.8 Secrets are stored as hashes, never as the original value

This applies to `users.password_hash` and to `refresh_tokens.token_hash`.

*Why:* If the database is ever read by someone who should not have it — a leaked backup, a compromised host — a stolen password hash is useless to them, and a stolen refresh-token hash cannot be replayed to log in. The server hashes the incoming value and compares hashes; it never needs the original. The same reasoning is why `caregivers.id_proof_number` no longer exists at all: data you never store cannot leak.

## 2. The tables

## SHARED

### 2.1 `users` — *Shared by both modules*

Every human who can log in: elderly people, family members, caregivers, and admins. One table, not four.

*Why one table:* Login, password reset, and JWT issuing are identical for all four roles. Four separate tables would mean four copies of that logic and an ambiguous answer to "which table do I check when this phone number logs in?". Role-specific extra data lives elsewhere — caregivers get their own `caregivers` table for professional details.

| Column | Type | Constraints | What it stores and why |
|---|---|---|---|
| `id` | UUID | PK, default `gen_random_uuid()` | Unique handle for this person. Every other table points here. |
| `phone` | VARCHAR(20) | NOT NULL, UNIQUE | Primary login identity. Chosen over email because many elderly users in India have a phone but no email address they check. 20 chars covers `+91` plus separators. |
| `email` | VARCHAR(255) | UNIQUE, nullable | Optional. Used for receipts and password reset when present. Nullable because we cannot require it. PostgreSQL allows many NULLs in a UNIQUE column, so this works. |
| `password_hash` | TEXT | NOT NULL | The bcrypt hash of the password. **Never the password itself.** `TEXT` because hash formats change length between algorithms and a fixed width would eventually truncate. |
| `full_name` | VARCHAR(120) | NOT NULL | Display name, shown on the family dashboard and in alert messages ("Ramesh pressed SOS"). |
| `role` | `user_role` enum | NOT NULL | One of `elderly`, `family`, `caregiver`, `admin`. Drives which home screen the app opens after login and which API endpoints are permitted. |
| `date_of_birth` | DATE | nullable | Age matters to caregivers and to emergency responders. Stored as a date, not an age — an age would be wrong within a year. |
| `gender` | VARCHAR(20) | nullable | Some families request a caregiver of a particular gender. Free text rather than an enum so it isn't a fixed list. |
| `preferred_language` | VARCHAR(10) | default `'en'` | ISO code (`en`, `hi`, `te`). Decides the app's language and, later, the language of SMS alerts. |
| `profile_photo_url` | TEXT | nullable | Link to an image in storage. The image itself is not in the database — storing binaries in PostgreSQL bloats backups badly. |
| `address_line` | TEXT | nullable | Street address. Read aloud to an ambulance dispatcher when GPS is not enough. |
| `city` | VARCHAR(100) | nullable | Used to match caregivers to a service area. |
| `state` | VARCHAR(100) | nullable | Same, plus disaster alerts are issued by state. |
| `postal_code` | VARCHAR(12) | nullable | Address completeness. |
| `is_active` | BOOLEAN | NOT NULL, default TRUE | Soft delete / suspension. A deactivated user cannot log in but their history survives. |
| `last_login_at` | TIMESTAMPTZ | nullable | Support diagnostics — "is this elderly user actually opening the app?" |
| `created_at` | TIMESTAMPTZ | NOT NULL, default `now()` | Registration moment. |
| `updated_at` | TIMESTAMPTZ | NOT NULL, default `now()` | Last profile change, maintained by trigger. |

### 2.2 `family_links` — *Shared* — **NEW in revision 2**

Which family members are allowed to see and manage which elderly users, and exactly what each of them may do.

**Why this is separate from `emergency_contacts`.** These two tables answer genuinely different questions, and conflating them causes real problems:

- `emergency_contacts` answers *"who do we phone when something goes wrong?"* — a neighbour with no app account belongs on that list.
- `family_links` answers *"who is allowed to open the app and watch this person's live location?"* — that is a privacy decision, and it is a much higher bar.

You would want a helpful neighbour called during an emergency without granting them permanent access to an elderly person's movements. Equally, a daughter living abroad may need full dashboard access without being the first person phoned. One table cannot express both without the permissions becoming a side effect of the phone list.

| Column | Type | Constraints | What it stores and why |
|---|---|---|---|
| `id` | UUID | PK | Handle for this link. |
| `elderly_user_id` | UUID | NOT NULL, FK → `users(id)` ON DELETE CASCADE | The person whose data is being accessed. |
| `family_user_id` | UUID | NOT NULL, FK → `users(id)` ON DELETE CASCADE | The person doing the accessing. Both cascade — if either account goes, the link is meaningless. |
| `relationship` | VARCHAR(50) | nullable | "Daughter", "Son", "Nephew". Shown in the app so the elderly user can see who has access in plain terms. |
| `permission_level` | `family_permission` enum | NOT NULL, default `'view'` | `view`, `manage`, or `owner`. A coarse label used for display and for defaults; the fine-grained booleans below are what the API actually enforces. |
| `can_view_location` | BOOLEAN | NOT NULL, default TRUE | May see live position and location history. **The most sensitive permission in the product** — it is the difference between care and surveillance. |
| `can_manage_contacts` | BOOLEAN | NOT NULL, default FALSE | May add or remove emergency contacts. Off by default: changing who gets called in an emergency should be a deliberate grant. |
| `can_manage_caregivers` | BOOLEAN | NOT NULL, default FALSE | May manage care plans, schedules, tasks and visits, and see bookings others made. Booking itself needs only an active link — there is no in-app payment, so a booking request commits no money. |
| `can_acknowledge_alerts` | BOOLEAN | NOT NULL, default TRUE | May mark an alert as seen and being handled. On by default — anyone trusted enough to be linked should be able to respond. |
| `status` | `link_status` enum | NOT NULL, default `'pending'` | `pending`, `active`, `revoked`. **A link does not grant anything until it is `active`.** This is what stops someone adding themselves to a stranger's account. |
| `invited_by` | UUID | FK → `users(id)` ON DELETE SET NULL | Who created the invitation. Audit trail for "how did this person get access?". |
| `approved_at` | TIMESTAMPTZ | nullable | When it was accepted. NULL while pending. |
| `revoked_at` | TIMESTAMPTZ | nullable | When access was withdrawn. The row is kept rather than deleted so the history of who had access, and when, survives. |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL | Audit. |

**Constraints:**
- `UNIQUE (elderly_user_id, family_user_id)` — one link per pair. Without it, two rows could disagree about permissions and the answer would depend on which one the query happened to read first.
- `CHECK (elderly_user_id <> family_user_id)` — nobody links to themselves.

*Why both a `permission_level` enum and individual booleans:* The enum is what the interface shows ("Full access" / "View only") because three options are understandable to a family. The booleans are what the API checks, because real permissions do not come in three tidy bundles — a son may manage caregivers but be denied location access. The enum sets sensible defaults; the booleans are the truth.

### 2.3 `refresh_tokens` — *Shared* — **NEW in revision 2**

Long-lived tokens that let the app get a new access token without asking for the password again.

**Why this table exists.** JWT access tokens are stateless and short-lived — the server can validate one without a database lookup, which is fast, but it also means the server cannot take one back. A token stolen from a phone stays valid until it expires. By storing refresh tokens, the long-lived credential lives in a table you control: revoke the row and that device is logged out on its next refresh, at most a few minutes later.

This is what makes "log out all my other devices" and "this phone was stolen" possible.

| Column | Type | Constraints | What it stores and why |
|---|---|---|---|
| `id` | UUID | PK | Handle for this token. |
| `user_id` | UUID | NOT NULL, FK → `users(id)` ON DELETE CASCADE | Whose session this is. Cascade: deleting a user logs out all their devices. |
| `token_hash` | TEXT | NOT NULL, UNIQUE | **A SHA-256 hash of the token, not the token.** The app holds the original; the database holds only a fingerprint. A leaked database therefore yields no usable sessions. |
| `device_label` | VARCHAR(120) | nullable | "Sree's Pixel 7". Shown on the active-sessions screen so a user can recognise which device to revoke. Meaningless labels make that screen useless. |
| `ip_address` | INET | nullable | Where the token was issued from. PostgreSQL's `INET` type validates the address and handles IPv4 and IPv6 correctly, which `VARCHAR` does not. |
| `user_agent` | TEXT | nullable | App and OS version at issue time. Useful for support and for spotting an unfamiliar session. |
| `issued_at` | TIMESTAMPTZ | NOT NULL, default `now()` | When it was created. |
| `expires_at` | TIMESTAMPTZ | NOT NULL | Hard expiry, typically 30 days. Every token dies eventually even if nobody revokes it. |
| `last_used_at` | TIMESTAMPTZ | nullable | Last refresh. Identifies dormant sessions worth cleaning up. |
| `revoked_at` | TIMESTAMPTZ | nullable | When it was invalidated. **NULL means live.** Kept rather than deleted so a security investigation can reconstruct what happened. |
| `revoked_reason` | VARCHAR(100) | nullable | `logout`, `rotated`, `password_change`, `admin_revoke`, `suspected_theft`. |
| `replaced_by_token_id` | UUID | FK → `refresh_tokens(id)` ON DELETE SET NULL | Self-reference: the token issued when this one was rotated. |
| `created_at` | TIMESTAMPTZ | NOT NULL | Audit. |

*The self-reference is worth explaining.* Good practice is to issue a fresh refresh token every time one is used and revoke the old one — token rotation. `replaced_by_token_id` chains them together. That chain detects theft: if an already-rotated token is presented again, either the legitimate app replayed it or an attacker is using a copy. Neither is safe, so the whole chain gets revoked and the user re-authenticates. Without the chain you cannot tell a stolen token from an ordinary one.

**Index:** `(user_id) WHERE revoked_at IS NULL` — the only frequent query is "which sessions are live for this user?".

### 2.4 `device_tokens` — *Shared* — **NEW in revision 2**

Expo push tokens, one row per physical device.

**Why a table rather than a column on `users`.** A user may have a phone and a tablet; a family member may install the app on their work phone as well. A single column holds one token, so the second device silently overwrites the first and that person stops receiving alerts without any error being raised anywhere. In an emergency product, a notification that quietly goes to the wrong device is the worst class of bug there is: nothing fails, nothing is logged, and the family simply is not told.

| Column | Type | Constraints | What it stores and why |
|---|---|---|---|
| `id` | UUID | PK | Handle for this device registration. |
| `user_id` | UUID | NOT NULL, FK → `users(id)` ON DELETE CASCADE | Who this device belongs to right now. |
| `expo_push_token` | TEXT | NOT NULL, UNIQUE | The token Expo's push service addresses. UNIQUE on the token alone, not on `(user_id, token)` — see the note below. |
| `platform` | `device_platform` enum | NOT NULL | `ios`, `android`, `web`. The delivery rules and payload limits differ per platform. |
| `device_name` | VARCHAR(120) | nullable | User-facing name, for the device list. |
| `device_model` | VARCHAR(120) | nullable | "Pixel 7", "iPhone 13". Support diagnostics — some delivery bugs are model-specific. |
| `app_version` | VARCHAR(20) | nullable | Which build is installed. Tells you whether a user has the fix yet. |
| `os_version` | VARCHAR(40) | nullable | OS version, same reason. |
| `is_active` | BOOLEAN | NOT NULL, default TRUE | Whether to send to this device. Set FALSE on logout or after repeated failures. |
| `last_seen_at` | TIMESTAMPTZ | nullable | Last time the app checked in. A device silent for months is probably gone. |
| `failure_count` | SMALLINT | NOT NULL, default 0 | Consecutive push failures. Expo reports permanently invalid tokens; after a few of those, stop trying. Reset to 0 on success. |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL | Audit. |

*Why the token is unique on its own:* Expo push tokens belong to an app installation, not to a person. If a phone is handed down, or two people share a tablet, the same token can legitimately move from one user to another. Making it unique per device and simply reassigning `user_id` on re-registration means the previous owner immediately stops receiving the new owner's alerts. A `(user_id, token)` uniqueness rule would allow both rows to exist, and the old user would keep getting notifications about someone else's emergencies — a privacy breach that would be very hard to notice.

## EMERGENCY MODULE

### 2.5 `emergency_contacts` — *Emergency module*

Who to call, and in what order, when something happens to a given elderly user.

**Note on scope after revision 2:** this table is now purely a notification list. Data-access permission moved to `family_links`. The `contact_user_id` column remains, but its meaning is narrower and worth being precise about — see the row below.

| Column | Type | Constraints | What it stores and why |
|---|---|---|---|
| `id` | UUID | PK | Handle for this contact entry. |
| `user_id` | UUID | NOT NULL, FK → `users(id)` ON DELETE CASCADE | **The elderly person this contact belongs to.** Cascade: if the user is gone, their contact list is meaningless. |
| `contact_user_id` | UUID | FK → `users(id)` ON DELETE SET NULL, nullable | Set when this contact also has an app account, purely so we can reach them by **push notification** as well as SMS. It grants no access to anything — that is `family_links`. NULL for a neighbour who only receives SMS. |
| `full_name` | VARCHAR(120) | NOT NULL | Who they are, shown in the alert log and read to responders. |
| `phone` | VARCHAR(20) | NOT NULL | The number Twilio dials or texts. Stored on this row rather than only on the linked user, because non-app contacts have no user row. |
| `email` | VARCHAR(255) | nullable | Optional secondary channel. |
| `relationship` | VARCHAR(50) | nullable | "Son", "Neighbour", "Family doctor". Gives a responder useful context instantly. |
| `priority` | SMALLINT | NOT NULL, default 1, CHECK 1–10 | Notification order. Priority 1 is called first. This is the column that makes "notify contacts in priority order" from Phase 1 possible. |
| `notify_by_sms` | BOOLEAN | NOT NULL, default TRUE | Per-contact channel preference. Some contacts should be texted but not called at 3am. |
| `notify_by_call` | BOOLEAN | NOT NULL, default TRUE | Same, for voice. |
| `notify_by_push` | BOOLEAN | NOT NULL, default TRUE | Only meaningful when `contact_user_id` is set — you cannot push to someone without the app. |
| `is_active` | BOOLEAN | NOT NULL, default TRUE | Temporarily mute a contact without losing them. |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL | Audit. |

**Constraint:** `UNIQUE (user_id, phone)` — the same number cannot be added twice for one user.

*Why priority is not unique per user:* Two contacts at priority 2 is acceptable (notify both simultaneously), and enforcing uniqueness would make reordering the list painful, since you cannot swap two values without a temporary third.

### 2.6 `geofences` — *Emergency module*

Safe zones drawn around a place. Used by Phase 3, defined now.

| Column | Type | Constraints | What it stores and why |
|---|---|---|---|
| `id` | UUID | PK | Handle for this zone. |
| `user_id` | UUID | NOT NULL, FK → `users(id)` ON DELETE CASCADE | The elderly person this zone applies to. Zones are per-person, not global — "home" is a different place for each user. |
| `name` | VARCHAR(100) | NOT NULL | "Home", "Morning park walk". Appears in the alert text: "Ramesh left Home". |
| `center_latitude` | NUMERIC(9,6) | NOT NULL | Centre point of the circle. |
| `center_longitude` | NUMERIC(9,6) | NOT NULL | Centre point of the circle. |
| `radius_meters` | INTEGER | NOT NULL, CHECK > 0 | How far from the centre still counts as inside. Metres rather than degrees, because a degree of longitude is a different distance at different latitudes. |
| `fence_type` | VARCHAR(20) | NOT NULL, default `'safe_zone'` | `safe_zone` (alert on leaving) or `restricted` (alert on entering, e.g. a busy road). |
| `alert_on_exit` | BOOLEAN | NOT NULL, default TRUE | Whether crossing outward raises an alert. |
| `alert_on_enter` | BOOLEAN | NOT NULL, default FALSE | Whether crossing inward raises an alert. Off by default — arriving home should be silent. |
| `is_active` | BOOLEAN | NOT NULL, default TRUE | Turn a zone off without deleting it (useful during a holiday). |
| `created_by` | UUID | FK → `users(id)` ON DELETE SET NULL | The family member who drew the zone. Answers "who set this up?" when a family disagrees about an alert. |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL | Audit. |

*Circles rather than polygons:* A circle is a centre and a radius — two numbers to check. A polygon needs point-in-polygon maths and either PostGIS or a library. Circles cover the real requirement (a house, a park) and can be checked on the phone as well as the server.

### 2.7 `locations` — *Emergency module*

The GPS trail. One row per position reading.

| Column | Type | Constraints | What it stores and why |
|---|---|---|---|
| `id` | UUID | PK | Handle for this single reading. |
| `user_id` | UUID | NOT NULL, FK → `users(id)` ON DELETE CASCADE | Whose position this is. |
| `latitude` | NUMERIC(9,6) | NOT NULL | Where. |
| `longitude` | NUMERIC(9,6) | NOT NULL | Where. |
| `accuracy_meters` | NUMERIC(6,2) | nullable | GPS confidence radius reported by the device. A fix accurate to 3 m is trustworthy; one accurate to 500 m should not trigger a geofence alert. **This column is what prevents false "he left the safe zone" alarms.** |
| `altitude_meters` | NUMERIC(7,2) | nullable | Reported by the device. Weak floor-level signal in a building; cheap to keep. |
| `speed_mps` | NUMERIC(6,2) | nullable | Metres per second. Distinguishes walking from being in a vehicle. |
| `heading_degrees` | NUMERIC(5,2) | nullable, CHECK 0–360 | Direction of travel. Useful on the live map. |
| `battery_level` | SMALLINT | nullable, CHECK 0–100 | Phone battery at the time of the reading. Explains a tracking gap ("the phone died") and lets the family be warned before it happens. |
| `is_moving` | BOOLEAN | nullable | Device's own motion flag. Lets the app report less often while stationary, saving battery. |
| `source` | VARCHAR(20) | NOT NULL, default `'gps'` | `gps`, `network`, or `manual`. A network-derived position is far less precise and should be treated differently. |
| `recorded_at` | TIMESTAMPTZ | NOT NULL, default `now()` | **When the device took the reading**, which is not when the server received it. Readings buffered offline arrive late; without this column they would appear out of order. |
| `created_at` | TIMESTAMPTZ | NOT NULL, default `now()` | When the server stored it. The gap between this and `recorded_at` is the sync delay. |

**Index:** `(user_id, recorded_at DESC)` — every read is "the latest positions for this user", and this index makes that instant.

There is no `updated_at`, because a position reading is a fact about a moment and never changes.

#### Retention policy: 30 days — **DECIDED in revision 2**

**Raw location points are kept for 30 days from `recorded_at`, then permanently deleted.**

*Why this is the right call:*

- **Volume.** At one reading per 30 seconds this table gains roughly 2,880 rows per user per day — about a million rows per user per year. It will be, by a wide margin, the largest table in the database. A 30-day window caps it at roughly 86,000 rows per user, which stays fast on modest hosting indefinitely.
- **Privacy.** Continuous location history is the most sensitive data this product holds. Keeping only what is useful is both the decent choice and the defensible one if a client or regulator ever asks why we hold it.
- **Nothing important is lost.** The positions that actually matter — where someone was when an alert fired — are copied onto the `alerts` row itself (§2.8) and are never touched by this cleanup. Purging location history does not erase a single emergency record. This is precisely why that denormalisation exists.

*Confirmed against a real feature, not just this original estimate:* Phase 3, step 2 landed the first continuous producer of this table — background location tracking, 90-second time floor with a 75-metre distance filter. Worst case (continuously moving) is roughly 960 rows/user/day; the typical case (mostly stationary) is far fewer. Both stay well inside the 2,880/day envelope above, so the 30-day retention policy and the volume assumption behind it still hold without any change.

*What is not being built now:* the deletion job itself. **The cleanup job is Phase 6**, per your decision. Until it runs, the table simply grows; at Phase 0 and 1 volumes that is harmless. The job will be a scheduled `DELETE FROM locations WHERE recorded_at < now() - INTERVAL '30 days'`, run daily in batches so it never holds a long lock.

*A note for whoever writes that job:* delete in chunks of a few thousand rows rather than in one statement. A single `DELETE` covering millions of rows takes a long transaction, bloats the write-ahead log, and can block writes — which in this product means blocking the recording of an emergency location.

### 2.8 `alerts` — *Emergency module*

The core table of the whole product: one row per emergency event.

| Column | Type | Constraints | What it stores and why |
|---|---|---|---|
| `id` | UUID | PK | Handle for this event. |
| `user_id` | UUID | NOT NULL, FK → `users(id)` ON DELETE CASCADE | Who the emergency is about. |
| `alert_type` | `alert_type` enum | NOT NULL | `sos`, `fall`, `geofence_breach`, `disaster`, `manual`. Decides urgency and message wording. |
| `status` | `alert_status` enum | NOT NULL, default `'active'` | `active` → `acknowledged` → `resolved`, or `cancelled` / `false_alarm`. **This is the column the family dashboard filters on.** An `active` alert is one nobody has responded to yet. |
| `severity` | `alert_severity` enum | NOT NULL, default `'high'` | `low`, `medium`, `high`, `critical`. An SOS press is critical; a geofence exit may be medium. |

| `location_id` | UUID | FK → `locations(id)` ON DELETE SET NULL | Link to the exact GPS reading. |
| `geofence_id` | UUID | FK → `geofences(id)` ON DELETE SET NULL | Which zone was breached, for `geofence_breach` alerts only. |
| `message` | TEXT | nullable | Free text, either typed by the user or generated ("Left Home safe zone"). |
| `triggered_at` | TIMESTAMPTZ | NOT NULL, default `now()` | When the emergency happened. Separate from `created_at` for the same offline-sync reason as `locations`. |
| `acknowledged_at` | TIMESTAMPTZ | nullable | When a human first responded. `acknowledged_at - triggered_at` is the single most important quality metric this product has. |
| `acknowledged_by` | UUID | FK → `users(id)` ON DELETE SET NULL | Who responded. |
| `resolved_at` | TIMESTAMPTZ | nullable | When it ended. |
| `resolved_by` | UUID | FK → `users(id)` ON DELETE SET NULL | Who closed it. |

| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL | Audit. |

**Denormalisation, kept per your instruction — and now load-bearing.** The coordinates are duplicated here even though `location_id` exists, for three reasons:

1. An SOS may fire before any GPS reading has been stored, or with location services switched off entirely. The alert still needs whatever position the phone could give.
2. `location_id` is `ON DELETE SET NULL`, so a purged location reading does not destroy the alert — it just unlinks.
3. **With the 30-day retention policy now decided, this is what makes purging safe.** An alert from four months ago still shows exactly where the person was, long after the location trail behind it is gone.

An alert without a location is a far worse failure than a duplicated number.

**Index:** partial index on `(user_id, triggered_at DESC) WHERE status = 'active'` — the dashboard's most frequent query is "any open alerts?", and a partial index keeps it fast no matter how large the history grows.

### 2.12 `caregivers` — *Caregiver module*

Professional details for a user whose role is `caregiver`. Extends `users`; does not replace it.

*Why a separate table:* Only caregivers have an hourly rate, qualifications and a verification status. Putting those columns on `users` would leave them NULL for every elderly and family user — noise on the majority of rows.

| Column | Type | Constraints | What it stores and why |
|---|---|---|---|
| `id` | UUID | PK | Handle for this caregiver profile. |

| `bio` | TEXT | nullable | Self-description shown to families browsing caregivers. |
| `experience_years` | SMALLINT | nullable, CHECK ≥ 0 | Years of experience. A key filter when families search. |
| `qualifications` | TEXT | nullable | Certificates and training, free text. |
| `specializations` | TEXT[] | nullable | Array: `{dementia, physiotherapy}`. An array rather than a join table because this list is short, read whole, and never needs its own attributes. |

| `hourly_rate` | NUMERIC(10,2) | nullable | Standard rate. The rate actually agreed is stored on the booking, since this one changes over time. |
| `currency` | CHAR(3) | NOT NULL, default `'INR'` | ISO 4217. |
| `service_area_city` | VARCHAR(100) | nullable | Where they work, matched against the family's city. |
| `id_proof_type` | VARCHAR(50) | nullable | **Which kind** of document was checked: `aadhaar`, `pan`, `driving_licence`. The type, never the number. |
| `id_verified` | BOOLEAN | NOT NULL, default FALSE | **New in revision 2.** Whether a human checked the document and it was valid. This is the entire outcome of identity verification, reduced to the one bit the system actually needs. |
| `verification_status` | `verification_status` enum | NOT NULL, default `'pending'` | `pending`, `verified`, `rejected`, `suspended`. The overall account state, which covers more than identity (references, training, conduct). **Only `verified` caregivers should be bookable** — this is the safety gate of the entire caregiver module. |
| `verified_at` | TIMESTAMPTZ | nullable | When verification happened. |
| `verified_by` | UUID | FK → `users(id)` ON DELETE SET NULL | Which admin verified them. Accountability — if a verification turns out to be wrong, you can find who did it. |
| `is_available` | BOOLEAN | NOT NULL, default TRUE | Currently accepting work. Distinct from verification — a verified caregiver may simply be full. |
| `average_rating` | NUMERIC(3,2) | NOT NULL, default 0, CHECK 0–5 | Cached average of their reviews. |
| `total_reviews` | INTEGER | NOT NULL, default 0 | How many reviews that average is based on. A 5.0 from one review is not a 5.0 from fifty. |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL | Audit. |

#### Identity numbers are not stored — **DECIDED in revision 2**

`id_proof_number` has been **removed from the schema entirely.** The verification record is now `id_proof_type` + `id_verified` + `verified_at` + `verified_by`: *which* document was checked, *whether* it passed, *when*, and *by whom*.

*Why this is better, not just safer:*

- Aadhaar and PAN numbers are regulated personal data. Holding them creates storage, disclosure and breach-notification obligations that a two-person project is not equipped to meet.
- The system never actually needs the number. Nothing in any phase reads it back. It would sit in the database purely as a liability.
- Data you do not store cannot leak, cannot be queried by a compromised API, and cannot appear in a log file or a database backup.
- The four columns that remain answer every question the product genuinely has: *has this person been checked, by whom, when, and against what kind of document.*

*What this deliberately gives up:* you cannot re-verify from stored data, or prove after the fact which specific document was seen. The document must be checked at the time and the result recorded. **You are raising the number-storage question with the client separately** — if they require it, the right implementation is almost certainly a hash plus the document held in a separate access-controlled store, not a plain column here.

*Why the rating is cached here:* A caregiver list screen shows twenty caregivers. Computing each average live means twenty aggregate queries over the reviews table on every scroll. Storing the result costs one recalculation when a review is written and makes the list instant. The trade-off is that the value can drift if it is not updated correctly — so it must be recalculated in the same transaction that inserts a review.

### 2.14 `schedules` — *Caregiver module*

One row per individual planned visit. A booking says "weekdays for three months"; `schedules` lists each actual visit.

| Column | Type | Constraints | What it stores and why |
|---|---|---|---|
| `id` | UUID | PK | Handle for this visit. |
| `booking_id` | UUID | NOT NULL, FK → `caregiver_bookings(id)` ON DELETE CASCADE | The agreement this visit comes from. |
| `caregiver_id` | UUID | NOT NULL, FK → `caregivers(id)` ON DELETE CASCADE | Who is visiting. |
| `elderly_user_id` | UUID | NOT NULL, FK → `users(id)` ON DELETE CASCADE | Who is being visited. |
| `visit_date` | DATE | NOT NULL | Which day. |
| `start_time` | TIME | NOT NULL | Planned start. |
| `end_time` | TIME | NOT NULL, CHECK > `start_time` | Planned end. |
| `status` | `schedule_status` enum | NOT NULL, default `'scheduled'` | `scheduled`, `completed`, `missed`, `cancelled`, `rescheduled`. `missed` is the one families care about most. |
| `notes` | TEXT | nullable | Anything specific to this visit. |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL | Audit. |

**Constraint:** `UNIQUE (caregiver_id, visit_date, start_time)` — **prevents double-booking.** The same caregiver cannot be scheduled to be in two places at the same moment. This is enforced by the database, not by application code, because application-level checks lose to race conditions when two families book simultaneously.

*The denormalisation here, kept per your instruction:* `caregiver_id` and `elderly_user_id` could both be reached through `booking_id`, but they are stored directly because "show me my schedule for this week" is the caregiver app's home screen and its single most frequent query. Storing these columns turns a three-table join into a single indexed lookup. The risk — that they could disagree with the booking's values — is contained by only ever setting them when the schedule row is created from its booking.

*Separate `DATE` and `TIME` rather than one `TIMESTAMPTZ`:* A caregiver's day is "9am to 11am" in local wall-clock terms. Storing it as an absolute instant means a daylight-saving or timezone change silently shifts every future visit. India has no DST today, but the schema should not depend on that staying true.

| `is_visible` | BOOLEAN | NOT NULL, default TRUE | Lets an admin hide abusive content without destroying the record. |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL | Audit. |

**Constraint:** `UNIQUE (booking_id, reviewer_user_id)` — one review per person per booking. Stops a single family inflating or tanking a caregiver's rating with repeat submissions.

*The sub-ratings are optional while the overall rating is required:* asking for four scores makes people abandon the form. One required number plus three optional ones gets a usable rating from everyone and detail from those willing to give it.

## 3. How the tables connect

Each relationship below is written as the real question it lets the app answer.

### Everything hangs off `users`

`users` is the hub. Seventeen of the nineteen tables reference it. The exceptions are `disaster_alerts` (a cyclone applies to an area, not a person) and `attendance` (which reaches users through its schedule).

### Shared relationships

| Relationship | The question it answers |
|---|---|
| `family_links.elderly_user_id` → `users.id` | **"Who is allowed to see this person's data, and what exactly may they do?"** Checked on every request that touches an elderly user's information. |
| `family_links.family_user_id` → `users.id` | **"Which elderly people can this family member open?"** Read on login to build the dashboard's list. This is the query that replaces the `emergency_contacts` workaround from revision 1. |
| `refresh_tokens.user_id` → `users.id` | **"Which devices are currently logged in as this person, and can I log one out?"** |
| `refresh_tokens.replaced_by_token_id` → `refresh_tokens.id` | **"Has this token already been rotated?"** If a rotated token is presented again, the session is compromised and the whole chain is revoked. |
| `device_tokens.user_id` → `users.id` | **"Which devices should receive a push for this person?"** Read on every push send. |

### Emergency module relationships

| Relationship | The question it answers |
|---|---|
| `emergency_contacts.user_id` → `users.id` | **"Who should we notify for this elderly person, and in what order?"** Read on every SOS press, sorted by `priority`. |
| `emergency_contacts.contact_user_id` → `users.id` | **"Does this contact have the app, so we can push as well as text?"** Nothing more — access is `family_links`. |
| `alerts.user_id` → `users.id` | **"What is this person's emergency history?"** |
| `locations.user_id` → `users.id` | **"Where is this person now, and where have they been in the last 30 days?"** Latest row is the live position; the trail is the map history, within the retention window. |
| `geofences.user_id` → `users.id` | **"Which safe zones apply to this person?"** Checked against each new location reading. |
| `alerts.geofence_id` → `geofences.id` | **"Which zone did they leave?"** Turns "an alert fired" into "Ramesh left Home at 3:14pm". |
| `alerts.location_id` → `locations.id` | **"Exactly which GPS reading triggered this?"** Goes NULL once that reading passes the 30-day window; the alert's own coordinates survive. |
| `notifications.alert_id` → `alerts.id` | **"Who did we tell about this emergency, and did it get through?"** The accountability trail. |
| `notifications.recipient_user_id` → `users.id` | **"Which alerts has this family member been told about?"** Drives the unread badge. |
| `notifications.emergency_contact_id` → `emergency_contacts.id` | **"Which contact entry did we use?"** Distinguishes the SMS to the neighbour from the push to the son. |
| `notifications.device_token_id` → `device_tokens.id` | **"Which specific handset did the push go to?"** Needed the moment a user has more than one device. |
| `ambulance_bookings.alert_id` → `alerts.id` | **"Did this emergency result in an ambulance, and what happened to it?"** |

### Caregiver module relationships

| Relationship | The question it answers |
|---|---|
| `caregivers.user_id` → `users.id` (UNIQUE) | **"What are this login account's professional details?"** One profile per account, enforced. |
| `caregivers.verified_by` → `users.id` | **"Which admin approved this caregiver, and when?"** The whole of the verification record now that the ID number is not stored. |
| `caregiver_bookings.elderly_user_id` → `users.id` | **"Which caregivers has this person had?"** |
| `caregiver_bookings.caregiver_id` → `caregivers.id` | **"Who is this caregiver working for?"** |
| `caregiver_bookings.booked_by_user_id` → `users.id` | **"Who arranged and authorised this?"** |
| `schedules.booking_id` → `caregiver_bookings.id` | **"What individual visits does this agreement produce?"** |
| `schedules.caregiver_id` → `caregivers.id` | **"What is this caregiver's schedule this week?"** The caregiver app's home screen. |
| `schedules.elderly_user_id` → `users.id` | **"Who is visiting my mother, and when?"** The family's view of the same data. |
| `attendance.schedule_id` → `schedules.id` (UNIQUE) | **"Did the caregiver actually turn up for this visit, and for how long?"** Planned versus actual. |
| `care_plans.elderly_user_id` → `users.id` | **"What are the standing care instructions for this person?"** |
| `activity_reports.elderly_user_id` → `users.id` | **"How has my mother been over the last two weeks?"** The family's daily read. |
| `activity_reports.schedule_id` → `schedules.id` | **"What was reported for this specific visit?"** |
| `activity_reports.care_plan_id` → `care_plans.id` | **"Is the care actually following the plan?"** |
| `tasks.care_plan_id` → `care_plans.id` | **"What concrete actions does this plan require?"** |
| `tasks.assigned_to_caregiver_id` → `caregivers.id` | **"What do I have to do today?"** The caregiver's task list. |
| `reviews.caregiver_id` → `caregivers.id` | **"How well rated is this caregiver?"** Shown when a family is choosing. |
| `reviews.booking_id` → `caregiver_bookings.id` | **"Is this review based on real work?"** Prevents fake reviews from people who never booked. |

### The one cross-module link

`alerts` and `schedules` both reference `users`, so the app can ask: **"Was a caregiver scheduled to be present when this emergency happened?"** That single question is the reason both modules share one database rather than each having its own. Neither module has to be built for it — the link exists as soon as both tables do.

## 5. Decisions taken, and what is still open

### Closed in this revision

1. **Family-to-elderly link** — separate `family_links` table with per-capability booleans. `emergency_contacts` is now purely a notification list.
2. **Refresh tokens** — stored, hashed, with rotation chaining and revocation reasons. Remote logout is possible.
3. **Device tokens** — own table, one row per device, unique on the token itself.
4. **Location retention** — 30 days, documented in §2.7. Cleanup job scheduled for Phase 6.
5. **ID proof numbers** — not stored. `id_proof_type` + `id_verified` + `verified_at` + `verified_by` instead.
6. **PostGIS** — not used. Circular zones only.

### Still open, but not blocking Phase 0

- **Medication modelling.** `care_plans.medications` and `activity_reports.medications_given` are free text. A structured medications table with dose, frequency and adherence would be the real answer, and Phase 4 may want it. Deferring is fine; the free-text columns can coexist with a structured table later.
- **Access-token lifetime.** Now that refresh tokens exist, the access token should be short — 15 minutes is a common choice, meaning a revoked session dies within 15 minutes. This is configuration, not schema, and will be settled at step 3 (auth).
- **What the client requires on identity numbers.** You are raising this separately. If they insist, the change is additive and will not disturb anything else.

## 6. The complete SQL

This will be saved as `backend/shared/db/schema.sql` once you approve. **It has not been run against any database.**

The order of statements matters: a table cannot reference another that does not exist yet.

```sql

-- ElderCare — Database Schema
-- PostgreSQL 14+   (no PostGIS)

--   psql -U postgres -d eldercare -f backend/shared/db/schema.sql
-- ============================================================================

-- Enum types
```
